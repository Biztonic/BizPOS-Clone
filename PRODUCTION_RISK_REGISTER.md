## Detailed Risk Profiles

### [P0-01] Ephemeral Release Keystore in CI Builds
- **File**: `.github/workflows/build_release_apk.yml`
- **Code Path**: Lines 33–40:
  ```yaml
  - name: Create Release Keystore
    run: |
      mkdir -p android/app
      keytool -genkey -v -keystore android/app/release.keystore -alias androiddebugkey -keyalg RSA -keysize 2048 -validity 10000 -storepass android -keypass android -dname "CN=Android Debug,O=Android,C=US"
      echo "storeFile=release.keystore" > android/key.properties
      echo "keyAlias=androiddebugkey" >> android/key.properties
      echo "storePassword=android" >> android/key.properties
      echo "keyPassword=android" >> android/key.properties
  ```
- **Problem**: Every automated GitHub Actions build creates a brand new random keystore. Each release APK generated by CI has a unique, mismatched signing signature.
- **Business Impact**: When merchants attempt to install an updated APK over an existing version, Android displays `INSTALL_FAILED_UPDATE_INCOMPATIBLE`. Merchants are unable to update the POS software without uninstalling first.
- **Security Impact**: Binaries labeled "Production Release" are signed using public, hardcoded debug credentials (`android`).
- **Data-Loss Impact**: **CATASTROPHIC**. Uninstalling the Android application purges `/data/data/com.bizpos.clone/`, immediately destroying the local SQLite database (`biztonic.db`) and all un-synced offline Hive data.
- **Recommended Fix**: Remove the runtime `keytool -genkey` block. Store the official production keystore in a base64-encoded GitHub Repository Secret (`RELEASE_KEYSTORE_BASE64`), decode it in CI, and inject credentials via environment secrets.
- **Regression Test Required**: Signature verification script comparing APK cert fingerprints across successive CI builds (`apksigner verify --print-certs`).

### [P0-02] Unauthenticated User Profile Read in Rules
- **File**: `firestore.rules`
- **Code Path**: Line 50:
  ```javascript
  match /users/{uid} {
    allow read: if (isAuthenticated() && (request.auth.uid == uid || isSuperAdmin())) || 
                 (resource.data.needsInitialPassword == true || resource.data.needsInitialPassword == 'true');
  ```
- **Problem**: Anyone on the public internet can read any user document where `needsInitialPassword` is set to `true`, without authenticating.
- **Business Impact**: Severe non-compliance with privacy legislation (GDPR / Indian Digital Personal Data Protection Act 2023). Exposure of merchant employee lists.
- **Security Impact**: Attackers can harvest merchant emails, employee roles, store assignments, and phone numbers to mount targeted social engineering attacks.
- **Data-Loss Impact**: Low.
- **Recommended Fix**: Remove the unauthenticated clause. Authenticate users via temporary onboarding tokens or Firebase Auth action codes before granting read access to user profile documents.
- **Regression Test Required**: Firestore unit test verifying unauthenticated `get(/users/target_uid)` returns `permission-denied` even when `needsInitialPassword: true`.

### [P0-03] Unauthenticated Pending Subscription Read
- **File**: `firestore.rules`
- **Code Path**: Line 126:
  ```javascript
  match /subscription_requests/{docId} {
    allow read: if isAuthenticated() || resource.data.status == 'PENDING';
  ```
- **Problem**: All pending subscription documents can be read without authentication.
- **Business Impact**: Leaks merchant payment transaction references, business names, owner emails, and requested POS plan tiers to competitors and scrapers.
- **Security Impact**: Public leak of commercial onboarding transactions.
- **Data-Loss Impact**: Low.
- **Recommended Fix**: Restrict read permissions strictly to `isSuperAdmin()` or authenticated owners matching `storeAccess(resource.data.storeId)`.
- **Regression Test Required**: Security rules test asserting unauthenticated `get` or `list` on `/subscription_requests` is rejected.

### [P0-04] Destructive Batch Data Purge Scripts in Root
- **File**: `firebase_full_cleanup.js`, `cleanup_firestore.js`, `firebase_manual_cleanup.js`
- **Code Path**: Root scripts:
  ```javascript
  // 1. Go to Firebase Console → Firestore → Rules
  // 2. Temporarily set rules to allow full access: allow read, write: if true;
  ```

- **Problem**: Dangerously documented manual scripts in the root directory that instruct operators to disable security rules and execute uncontrolled batch deletions. (Already caused total production database loss previously as documented in `DATA_RECOVERY_README.md`).
- **Business Impact**: Catastrophic operational shutdown if run by developers or automated tooling.
- **Security Impact**: Direct circumvention of all Firestore security rules.
- **Data-Loss Impact**: **TOTAL PERMANENT DATA LOSS** across all cloud collections.
- **Recommended Fix**: Relocate or remove these scripts from the active workspace. Add an immutable environment check and require multi-party approval or Firebase Admin SDK emulator safeguards.
- **Regression Test Required**: Pre-commit hook or CI check preventing scripts with `allow read, write: if true` from entering the codebase.

### [P1-01] Web Checkout Asymmetry & Missing Inventory Ledger Persistence
- **File**: `lib/features/billing/application/checkout_orchestrator.dart`
- **Code Path**: Lines 194–213:
  ```dart
  if (!kIsWeb) {
    // NATIVE: Atomic SQLite transaction (Order + Movements + Event + Counter)
    await _repository.performAtomicCheckout(...);
  } else {
    // WEB: Standard Repository Write
    final insertResult = await _billingRepository.insertOrder(enrichedOrder);
    await _tokenService.incrementOrderCounter(params.activeStoreId);
  }
  ```
- **Problem**: On Flutter Web, `inventory_movements` and `business_events` are never written to any persistent database or queued for Firestore sync during checkout. Only `cache_inventory` in-memory quantity is decremented.
- **Business Impact**: Web POS transactions cause irreversible stock drift between actual inventory counts and the stock ledger, compromising auditing and financial reporting.
- **Security Impact**: The append-only immutable financial audit ledger has gaps for all Web-originated sales.
- **Data-Loss Impact**: High (movements and ledger events are discarded on Web).
- **Recommended Fix**: Implement Web persistence for `inventory_movements` and `business_events` via `BillingRepositoryImpl`, queuing them to `sync_queue_v2`.
- **Regression Test Required**: Cross-platform checkout test asserting that Web checkouts write movements to the sync queue.

- **Problem**: Production UI widgets bypass repositories and perform raw Firestore queries and mutations directly.

- **Regression Test Required**: Offline simulated widget tests verifying screens load correctly when network is disconnected.

### [P1-03] Anonymous Authentication Fallback in PIN Login
- **File**: `lib/widgets/employee_pin_dialog.dart`
- **Code Path**: Lines 232–240:
  ```dart
  if (FirebaseAuth.instance.currentUser == null) {
    try {
      await FirebaseAuth.instance
          .signInAnonymously()
          .timeout(const Duration(seconds: 5));
    } catch (e) {
      debugPrint("Auth non-critical failure: $e");
    }
  }
  ```
- **Problem**: Employee PIN dialog attempts anonymous sign-in if no Firebase Auth session exists.
- **Business Impact**: If anonymous sign-in is disabled in the Firebase Console, PIN authentication fails. If enabled, it creates thousands of orphaned anonymous user accounts in Firebase Auth over time.
- **Security Impact**: Anonymous accounts have unmanaged lifecycles and may satisfy generic `isAuthenticated()` rules in Firestore.
- **Data-Loss Impact**: Low.
- **Recommended Fix**: Use stored terminal session tokens or authentic custom token exchange instead of creating anonymous Firebase Auth accounts for local employee switches.
- **Regression Test Required**: Unit test validating offline PIN login without triggering `signInAnonymously()`.

### [P1-04] Arbitrary 70% COGS Estimation in Financial Reports
- **File**: `lib/providers/order_provider.dart`
- **Code Path**: Lines 566–567:
  ```dart
  if (items.isEmpty && !isRefunded) {
    categoryAggregations['Uncategorized']!['cogs'] =
        categoryAggregations['Uncategorized']!['cogs']! +
            (effectiveTotal * 0.7);
  ```
- **Problem**: When calculating sales statistics on Web, if an order record has an empty items list, the system estimates the Cost of Goods Sold (COGS) by multiplying total sales by 70%.
- **Business Impact**: Reports display fictitious profit margins and COGS numbers, misleading business owners and compromising tax filings.
- **Security Impact**: Financial statement inaccuracy.
- **Data-Loss Impact**: Analytics data distortion.
- **Recommended Fix**: Categorize orders without item cost data as "Unknown COGS" with an explicit warning banner in financial dashboards.
- **Regression Test Required**: Unit test verifying orders with empty items yield 0.0 or null COGS rather than a synthesized 70% calculation.

### [P2-02] Dual State Management (Provider + Riverpod)
- **Files**: `lib/providers/` vs `lib/features/**/providers/`
- **Problem**: Dual state management frameworks (`Provider` and `Riverpod`) manage parallel representations of the same domains (`OrderModel` vs `OrderEntity`, `InventoryItem` vs `InventoryEntity`).
- **Business Impact**: Increases cognitive load, slows feature development, and introduces bugs when UI screens read different providers.
- **Recommended Fix**: Standardize incrementally on Riverpod notifiers and single canonical domain entities.

### [P2-03] Empty Firestore Composite Indexes
- **File**: `firebase_indexes.json`
- **Code Path**: Lines 1–4 (`"indexes": []`)
- **Problem**: No composite indexes are registered in version control.
- **Business Impact**: Queries combining `storeId` with ordering on `date` or `createdAt` will fail in production once dataset size exceeds small-collection thresholds.
- **Recommended Fix**: Generate and check in compound index definitions for `orders(storeId, date DESC)` and `inventory_movements(storeId, createdAt DESC)`.
